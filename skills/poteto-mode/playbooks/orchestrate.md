### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of Orca workers, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with Orca's own tools. Load the `orchestration` skill and start workers with `ORCA orchestration worker-start`, then end your turn. Orca wakes you when a worker reports, asks, or stops. Keep the program's state in `notes.md` under `~/.claude/projects/<slug>/orchestrate/<project-slug>/` and in the Run's Tasks (`task-create --deps`, `task-list --ready`). Each owner watches its own PR per `playbooks/babysit.md`. Call no scripts, run no polling loops, and never relay messages or status between agents. A `check` run from a script takes your mail, so Orca has nothing left to wake you with.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its spec carries everything it needs, including each upstream report it depends on, pasted in full, and goes in through `--spec-file`. Workers can't see their siblings. A worker that writes gets its own worktree (`--worktree new-child`, or `new-top-level` for independent work). Use `--worktree current` only when the task reads without writing or needs this checkout's state. When an Orca server is paired, put heavy work there with `--on <server>`, after loading the orchestration skill's `references/placement-and-remote.md`, unless the work needs this machine: a runtime check through a control skill, local transcripts, a simulator, or auth that exists only here. Pick each worker's effort for the job, per the Subagents section.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and specs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Reuse a worker's worktree when new work needs its built state,** such as its checkout, uncommitted changes, or a running process: start the new worker there with `--worktree path:<path>`. Message a worker with `ORCA orchestration send --to dispatch:<dispatch_id>` only for a follow-up on the same work. Never message one to check on it, because a message restarts an idle agent. Probe read-only with `worker-show`, `worker-read`, and `worker-list`.
- **Each PR gets a verifier that isn't its author,** on a different agent, such as `codex` for a `claude` owner. The owner merges only on that verifier's pass at the current head.
- **Start with one unit.** Take it through spec, owner, verifier, and merge before you fan out, so a flaw in the spec costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each spec names the evidence that proves the work is done,** such as a command and its expected output, a control-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's specs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope. A worker in its own worktree stays open after it finishes, so release it with `worker-release` once nothing needs its chat.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Silence alone never proves a worker exited, so stop and retry it per the orchestration skill's `references/recovery-and-cleanup.md`. Retry by cause: a smaller scope after a context or memory limit, the same spec after a dropped connection, and a different agent after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **After an Orca restart, reattach by PR and branch.** Terminal handles are stale and in-process subagents are dead, but workers on a paired server are not. Re-read `notes.md`, then list what survived with `ORCA orchestration worker-list --run <run_id> --include-remote --json`.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
